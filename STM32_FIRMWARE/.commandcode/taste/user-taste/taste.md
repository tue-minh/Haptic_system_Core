# User Taste
- User develops on Windows and uses PowerShell (prompt shows `PS D:\...`); prefer PowerShell syntax for shell commands and Windows-style paths (e.g., `python examples\stepper_demo.py COM7`, backslash separators). Confidence: 0.85
- Prefers interactive scripts/consoles that start running first, then let the user type/pick options (menus, prompts) at runtime — rather than requiring all arguments up front before the program runs. Confidence: 0.75
- Expects documentation (e.g. protocol docs, READMEs) to be kept in sync with code changes — when behavior/interfaces change, update the docs as part of the same task rather than leaving them stale. Confidence: 0.7
- Expects related code layers to stay consistent when interfaces change — e.g. when rewriting a firmware driver, also consider whether the Python host client (python/tue_acsi) needs updating, rather than treating layers in isolation ("update all"). Confidence: 0.8
- Drives the whole firmware build/flash cycle through VS Code tasks (`.vscode/tasks.json`) rather than ad-hoc CLI commands: delete the old build, rebuild, convert ELF→BIN, then flash via USB DFU (`dfu-util`). Treat tasks.json as the canonical build/flash entry point. Confidence: 0.6
- Prefers the agent to carry a multi-step plan through to completion autonomously rather than pausing to ask for confirmation between steps; gets impatient with requests like "do the rest task!!!" / "have you done yet" when work is left unfinished. Confidence: 0.7
- Prefers deliverables written to files instead of chat: notifies the agent it doesn't need to reply in chat ("dont need to answer me back in this chat") and wants the work product captured on disk. Confidence: 0.8
- Wants a markdown summary/report file listing everything that was done at the end of a task ("list all worked you've done in a markdown file"), including which spec items were satisfied. Confidence: 0.8
- Hands over a spec/update markdown file (e.g. `USB_STM32_UPDATE.md`) and expects the agent to read it and implement every task it lists end-to-end without further direction. Confidence: 0.7
- Wants complete implementations with full parity to the referenced library — when porting/adapting a library, expose ALL of its functionality (every instruction, every API surface, e.g. SYNC_READ, RESET_TURNS, whole register map) rather than a partial subset; states this emphatically ("IMPLEMENT ALL THE CODE RELATED TO ..."). Confidence: 0.7
- When a reference implementation is provided, wants the rewrite to faithfully follow its architecture and design patterns (e.g. restructuring a monolithic driver into the reference's layered regs/protocol/hal design) rather than keeping the old structure. Confidence: 0.7
- Prefers simple, plain GUI/app designs over colorful ones ("Dont make it colorful, make it simple") — favor minimal, functional UI over decorative styling. Confidence: 0.7
- Wants GUI control surfaces to be comprehensive: expose all relevant functions grouped within each control tab (e.g. list every function in each motor control tab) rather than hiding them behind nested views or scattered across screens. Confidence: 0.65
- Wants command output displayed as the human-readable response/feedback of each command (e.g. "pos=57 (5.0 deg)") rather than raw or parsed packet frames (no TX/RX/CRC packet inspectors). Confidence: 0.7
- Expects a command's feedback/response to be shown right where the command is triggered (its own feedback box in the same tab, always visible) rather than only in a single shared panel elsewhere; asks "where is the feedback...?" when it isn't co-located with the controls. Confidence: 0.6
- When testing against live hardware, restrict verification to safe/read-only operations and do not actuate motors or cause physical motion unless explicitly told otherwise (e.g. "you can test it but do not run the motor"). Confidence: 0.6
- Expects new firmware modules/drivers to be actually wired into the RTOS task setup (e.g. `freertos.c`) and runnable, not just compiled — asks how to "run it" when a module isn't invoked from the task layer. Confidence: 0.55
- Expects code to land in the exact files the spec names: when a task document says to add code to e.g. `Core/Inc/tue_usb_binary.h` / `Core/Src/tue_usb_binary.c`, implement it there instead of splitting it into a new library/module file; challenges deviations ("why you not write in ... instead of separate it into new library file"). Confidence: 0.75
- Wants the reasoning explained before code is touched when the agent's approach diverges from the request/spec: says "dont code and fix any code yet, tell me why..." — present the justification, the tradeoff/cost, and the alternative, then let them decide the refactor. Confidence: 0.7
