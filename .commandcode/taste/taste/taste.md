# Taste
- Prefers plain, uncluttered interfaces: explicitly asked to avoid a colorful UI and "just make it simple" — decorative colour (axis-tinted readouts, accent buttons, coloured headers) should be stripped in favour of neutral greys. Confidence: 0.85
- Accepts colour only where it carries information (status LEDs, destructive/stop actions, a monochrome-by-default data colormap); distinguish other elements by lightness and line style rather than hue. Confidence: 0.7
- Prefers a light theme with a bright background over a dark one; lighter surfaces are the desired default look. Confidence: 0.65
- When a known-working reference implementation exists, follow it rather than written specs or docs where they conflict — explicitly asked to "just make it following these files" after a spec-derived divergence broke real hardware behaviour. Confidence: 0.8
- Trusts empirical evidence from actually running the working code/hardware over spec assumptions; treats "the reference ran with no error" as the authority to match. Confidence: 0.7
- For hardware control surfaces, expects directional controls to be arranged spatially to mirror the physical axes and their sign conventions — jog buttons grouped per axis, one pair vertical and the other horizontal, with an explicit sign order stated (Z− above Z+, X− above X+, Y+ left of Y−) — rather than as a flat list of buttons. Confidence: 0.7
- Drives work through in-repo markdown task/spec files (e.g. a `TODO_*.md` with numbered instructions, protocol constants and acceptance vectors) and expects the agent to read them and complete all listed tasks end-to-end, not just the headline feature. Confidence: 0.7
- Wants GUI features to mirror the reference tool's UX (e.g. live reference-style pyqtgraph taxel view over a slower throttled alternative, automatic port assignment) rather than diverge into novel designs. Confidence: 0.7
- Expects hardware problems to be reproduced by actually running against the real device rather than reasoned about from code, and volunteers deliberately conservative test settings when handing over hardware (e.g. "just move with minimum velocity (1mm/s) and minimum acceleration (50mm/s2)") — so use the safest parameters that still reproduce. Confidence: 0.65
- When the upstream reference library changes protocol/API, expects the consuming project's whole communication core to be re-wired end-to-end onto the new API (including stale references and tests), not partially patched. Confidence: 0.6
- Frames hardware bugs as "firmware issue or this GUI issue" and wants the root cause explicitly attributed with evidence, rather than a fix applied blindly on either side. Confidence: 0.55
- Expects a reported bug to come back as an actual fix, not a diagnosis followed by "want me to implement that?" — when the user says "fix for me" / "recode for me", or pastes a traceback, they want the change made and verified in the same turn, with the diagnostic narrative kept brief. Confidence: 0.8
- Reports bugs by pasting the raw application log/output verbatim (timestamps, error lines, disconnect sequence, Python traceback) instead of prose repro steps, and expects the agent to mine that log for the failure signature and act on it — no clarifying questions about what was pasted. Confidence: 0.65
- After a fix is claimed, an unchanged behaviour is reported flatly as "still has the bug" with no new analysis on their side; treat that as "the previous theory was wrong, keep digging against the real device" rather than re-explaining the earlier fix. Confidence: 0.55
- Follows up with very terse, uncorrected messages ("still has the bug ... fix for me. Still com14", "in sensor, make it auto detection id address") and expects the agent to infer the context from the ongoing work — including reusing the same device/port/setup already established — without asking to re-confirm it. Confidence: 0.65
- Prefers hardware links to configure themselves: device addresses and COM ports should be auto-detected (sweep/probe on connect, auto-assign detected ports to roles) instead of asking the user to select addresses or ports by hand, while still allowing an explicit override. Confidence: 0.7
- Expects the software's connection model to mirror the real physical cabling exactly: if one physical port carries several protocols (e.g. motor control and haptic output on the same STM32 COM port), they must be multiplexed on that one link rather than exposed as a separate port — one port per physical cable, nothing invented. Confidence: 0.7
- Verifies UI work visually and by behaviour, not by claim: renders/inspects the result and re-runs the test suite, and expects the agent to do the same — including catching layout regressions (window minimum width, clipped labels, toolbars forcing a window wider than the screen) that a build-only check would miss. Confidence: 0.6
- For embedded firmware that drives physical actuators (valves, DACs), expects a safety-first boot: every output must be forced to its safe state (0 V / off) at power-up before anything else runs, and held there until fully valid control data arrives — imposed as an explicit review requirement even when the reference code didn't do it. Confidence: 0.7
- Diagnostic interfaces (e.g. USB serial console) must be strictly debug-only and non-blocking — gated on availability, bounded work per loop pass, printing only on command/boot — so they can never delay or affect the real-time control path. Confidence: 0.7
